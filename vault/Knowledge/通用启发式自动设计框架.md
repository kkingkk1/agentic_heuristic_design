# 通用启发式自动设计框架

更新日期：2026-11-03。

本文件是跨阶段的已确认方法事实源。[主计划](../Plan/mechanisms/多智能体协作的通用启发式自动设计.md)保存研究目标与阶段路线；各阶段执行与验收见对应阶段计划。以下 3.x 编号属于本文件的方法合同。代码块为设计伪代码，项目尚无已验收的系统实现。

## 研究对象与输入

在给定求解框架中自动设计输入指定的启发式模块。用户提供问题、模块职责、函数签名、必要调用上下文、实例与运行要求，无需提供模块初始实现。

候选只能修改指定模块、内部辅助函数与获准参数。固定调用代码、公共配置、约束、原始目标、求解停止规则与评价脚本由控制程序管理。

每个个体包含 Thought、Code、Fitness：

- Thought：描述实际启发式规则，与代码对应。
- Code：完整可调用函数及获准参数。
- Fitness：由完整有效的任务评价结果计算，未评价或无效时没有正常 Fitness。

候选使用唯一 ID，代码修改后产生新 ID。生成角色／算子、父候选、代次、轮次和评价结果通过该 ID 关联。任务、模型、数据、种子与资源配置在每次运行记录中保存一次；首版只做本次运行内的代码去重，通用缓存按实际需要后置。

## RoCo 主流程

只将 Explorer／Exploiter 的任务目标替换为收益 Q／速度 E，保留 Critic、Integrator 和 RoCo Algorithm 1 的其余流程：

1. 控制程序用 EoH 无种子提示生成 30 个原始提案，统一评价并记录错误，对有效候选代码去重后取 N=10 个。
2. 每代从原种群执行 E1/E2/M1/M2，每算子 N 个提案，结果留到代末。
3. 按 RoCo 排名概率选择两个不同精英 A/B；Critic 先比较，Q/E 均从 B 启动。
4. 正式协作三轮。每轮 Critic 比较当前双分支，Q/E 各自提案并评价，Integrator 融合本轮两个有效新提案并评价。
5. 有效新提案直接续写，即使分数下降；无效时沿用上一有效状态。协作结束后，两支各从正式轮次有效提案中按同一 Fitness 选优，执行末轮精英融合。
6. Q/E 分别总结本代长期反思，Integrator 合并。以本代最初的 A/B 为基底，各做 Q/E/I 三方向变异，共六个。
7. 合并 EoH 输出、最后轮 Q/E/融合输出、末轮精英融合和六个变异，准入、去重后取 Top N；原父代、启动状态与早轮候选不自动保留。
8. 变异评价与筛选完成后，把本代 Q/E/I 经验按角色和代次追加到历史，供后续代读取。

初始化生成方式来自 EoH §3.4，数量来自 RoCo 附录 D。RoCo 未详述完整初始化生成过程；这一组合与失败处理属于本项目接入约定。参考启发式只用于工程接入检查，不进入初始化提示或种群。

## 角色与提示

### 3.4 各角色的读取权限与输出格式

本节依据 [RoCo 原文](../References/RoCo/2025__Xu__RoCo_Role-Based_LLMs_Collaboration_for_Automatic_Heuristic_Design.pdf) PDF 第 10 页 Algorithm 1 与第 13–16 页 Prompt 1–10。只将 Explorer／Exploiter 的任务目标替换为 Q 的目标值改进／E 的计算提速，其余角色的输入内容与输出要求沿用论文。初始种群生成见 §3.7。

#### 按阶段提供论文规定的输入

共同的 `task_description` 包含本任务的问题、模块职责、接口和原始目标方向。候选 ID、代次、轮次和评价记录由控制程序保存，不自动进入模型提示。

- **初始 Critic，Prompt 5：** 读取任务说明、两个原始精英的代码与目标得分，区分较优和较差程序。输出短期反思与改进建议。
- **协作启动 Q/E，Algorithm 1 第 6–8 行与 Prompt 1–2：** 两者均读取第二个精英 B 的算法描述、代码、目标得分，以及初始 Critic 的建议和反思。A 的代码不再附入这两个调用。
- **每轮 Critic，Algorithm 1 第 10–11 行与 Prompt 6–8：** 比较当前 Q/E 两个已评价候选，读取两者的算法描述、代码和目标得分。论文的 `invalid_ind_prompt` 仅承载相关无效程序提示，不扩展为整份运行日志。每轮调用一次，输出供两支使用的反思和建议。
- **每轮 Q/E，Prompt 1–2：** 各自读取自己的当前候选描述、代码、目标得分，以及本轮 Critic 的建议和反思。不额外附入对方候选代码、原始双精英或整份角色历史。Prompt 1–2 未说明 `Reflection` 占位符的完整存储来源；本项目用本次 Critic 的 `<ref>` 内容填入，与 `<ans>` 建议分别提供，不新增另一份记忆输入。
- **逐轮 Integrator，Prompt 3：** 读取任务说明、本轮 Q/E 两个新提案各自的算法描述、代码与目标得分，以及论文的代码生成输出要求。不额外附入 Critic、原始精英对、历史记忆或额外计时报告；论文未完整说明会话上下文管理。
- **末轮精英融合，Prompt 4：** 从两支第 1 至第 T 轮正式有效提案中，分别按同一目标值适应度选出最佳候选。只读取任务说明、两份入选代码及其目标得分、Reflection summary 和代码生成输出要求；只提供 Prompt 4 所列字段。summary 按 §3.8 编排已有短期反思。
- **Q/E 本代长期反思，Prompt 9 与公式 15：** 读取任务与角色说明、本代短期反思和对应的目标值变化，分别总结本代经验。不附入程序代码、完整耗时、运行剖析或全部实验记录。
- **整合长期反思，公式 16 与 Algorithm 1 第 27 行：** Integrator 只合并本代 Q/E 两份长期反思，不额外读取候选、评价报告或整批协作证据。
- **三方向精英变异，Prompt 10 与公式 17：** 每次读取任务说明、一个原始精英的代码、对应角色的本代长期反思与此前历史反思，以及代码生成输出要求。不额外附入该精英的 Thought、目标得分或另一个精英。

所有目标得分来自独立评价；提示中的优劣关系按任务原始目标方向解释，不能把最小化示例里的“越低越好”套用于 OP、MKP。耗时仍独立测量和报告，但不作为新增角色输入；E 的区别限于任务目标文字。

#### 输出沿用论文提示

**Critic：** 初始与逐轮比较输出反思和建议：

```text
<ref>短期反思</ref>
<ans>具体评价与改进建议</ans>
```

Prompt 5 的格式要求反思至多 30 个英文词、建议至多 40 个英文词，正文还要求设计提示少于 20 词。逐轮 Prompt 6–8 的建议至多 40 个英文词；不把初始反思的 30 词上限扩成所有阶段的统一约束。原文个别标题与正文的“当前更好／更差”标签不一致，按实际目标得分与提示正文核对，不能据标题给出相反结论。

**Q/E 本代长期反思，Prompt 9：**

```text
<ans>围绕该角色总结的本代长期经验</ans>
```

单次总结少于 50 个英文词。这个限制不等于历史记忆总容量。

**代码生成，Prompt 1–4、10：** 原文使用 `{output_request}` 占位符，没有展开统一的包裹标签或完整语法。代码生成保留算法思路与完整模块代码的内容要求。[P0 任务1](../Plan/mechanisms/P0-单任务一代接入与验收.md#2026-11-03-实测与复现)登记了项目约定的解析方式，并用无种子提案完成单次验证；这不是论文公开的统一输出协议。其他生成阶段仍须按该约定验证实际响应。候选仍按 Thought、Code、Fitness 保存，Fitness 由评价器计算；不同阶段只读取上述提示明确包含的字段。

**整合长期反思：** 论文定义 Merge，但未给出独立格式模板。输出合并后的经验文本，不另加事实表、证据字段或额外决策类型。

#### 控制程序负责记录与异常处理

合法性、错误记录、预算与失败回退沿用 §3.11。当前版本不向原生成方发起候选代码修复请求。输入无效而无法调用融合时，由控制程序记录跳过；不要求 Integrator 输出 `SKIP`，也不因输入重复或模型认为机制不兼容而取消论文规定的融合槽位。模型只按相应阶段的论文提示生成内容，控制程序负责登记、评价和状态更新。

## 评价合同

正式任务为 ACO＋TSP、CVRP、OP、MKP、离线 BPP，以及 GLS＋TSP。ACO 的白盒与黑盒分别运行和报告；规模、迭代和数据要求以[P1 任务与数据合同](../Plan/mechanisms/P1-任务与正式对照接入.md)为详细来源。

设 $J(h,i)$ 为固定框架使用候选 $h$、在训练实例 $i$ 上完成规定求解后的原始目标，训练集为 $D$：

$$
\bar J(h)=\frac{1}{|D|}\sum_{i\in D}J(h,i),
\qquad
F(h)=
\begin{cases}
-\bar J(h), & \text{原问题最小化},\\
\bar J(h), & \text{原问题最大化}.
\end{cases}
$$

TSP、CVRP、BPP 最小化；OP、MKP 最大化。符号转换只统一排序方向，原始目标始终保存。父代排名、正式轮次选优、Top N 和最终选择均按同一 Fitness，同分按生成顺序，耗时不参与排序。

直接复用经核验的任务 `eval.py`／`eval_black_box.py`。脚本导入候选并执行固定框架，完成合法性检查、原始目标和平均值汇总；缺项在原任务脚本中局部补齐。控制程序准备独立目录、监督子进程、读取原有结果并记录开销，不另建通用验证评分层。调用方式见[P0 的评价调用方式](../Plan/mechanisms/P0-单任务一代接入与验收.md#评价调用与检查)。

### 3.3 RoCo 目标值适应度与统一排序

适应度定义如上。按固定求解预算下的训练集平均原始目标计分；TSP/CVRP/BPP 最小化，OP/MKP 最大化。内部 Fitness 统一越大越好，同分按生成顺序排序，耗时单独记录。

父代排名、正式轮次选优、Top N 与最终程序选择使用同一规则。不同任务、规模或评价合同的分数不混排。完成规定求解且结果合法即可计分；硬超时、未完成全部评价、非法输出或技术异常不能获得正常 Fitness。

Q 侧重改善目标值，E 侧重减少计算成本。有效新提案直接成为下一轮状态，即使分数下降；无效时按 §3.11 回退。耗时和运行剖析用于事后分析，不额外进入 §3.4 的角色输入。

## 候选与运行记录

### 3.5 候选表示

候选保留以下最小表示；Code 文件及获准参数发生修改时使用新的候选 ID。

```python
@dataclass
class Candidate:
    candidate_id: str
    description: str       # Thought
    source_path: str       # 完整 Code，包含获准参数
    fitness: float | None = None  # 仅由完整有效评价回填
```

来源记录通过候选 ID 关联生成角色／算子、父候选、代次与轮次；经验按 Q/E/I 和代次保存。任务、模型、提示、代码来源版本、数据、随机种子与资源配置在本次运行记录中保存一次，不要求每个候选重复携带整套哈希。

运行记录保存脚本原有逐实例结果、平均原始目标、Fitness、完整耗时、失败原因和实际开销。代码完全相同的候选在种群中只占一项，保留最早完整有效评价及各次实际开销。当前只实现本次运行内的代码去重；通用结果缓存待出现实际需求后再设计。

## 初始化与代内协作详细合同

### 3.7 初始种群建立

控制程序按 EoH 无种子提示生成 30 个原始提案，提供任务、模块和接口，不提供已有启发式代码。所有提案先生成 Thought 与 Code，再按相同任务脚本评价；技术错误只记录，失败提案不进入有效候选集。完成 30 次原始生成后对有效候选按代码去重、Fitness 排名，取 N=10 个。

有效不同候选不足 N 时记录初始化失败并停止。已有参考函数只用于 P0 接入核验，不进入提示或种群，也不作为数量不足时的补齐。初始化生成、评价与失败的实际开销计入研发成本，Q/E 不分别建立冷启动种群。

### 3.8 EoH 外层、双精英与代内协作

1. 从本代原种群执行 E1/E2/M1/M2，每算子生成 N 个提案并评价。EoH 输出留到代末，不提前更新父代种群；算子自身的父代规则按来源接入。
2. 从同一原种群按 RoCo 附录 E 的排名概率抽取两个不同精英 A/B，名次索引从 0 开始，权重为 `(i+1)^(-3)`。第二个从第一个之后 +1 或 +2 的合法位置等概率选择；无合法后继则按条件分布重采样。不足两个候选时停止。
3. Critic 先比较 A/B。Q/E 均以 B 为代码基底启动，分别评价为 h0；启动不计入正式三轮，也不自动进入生存池。
4. 每轮 Critic 比较当前 Q/E，一次输出供两支使用。Q/E 各自生成新提案并评价；有效时直接续写，无效时沿用上一有效状态。
5. Integrator 按 Prompt 3 融合本轮两个有效新提案并评价。任一输入无效时由控制程序记录该槽位未执行；融合不改变下一轮两支的独立基底。
6. 三轮后，各支只从 h1 至 h3 的正式有效提案中按统一 Fitness 选最佳，再按 Prompt 4 做末轮精英融合。summary 只按顺序编排已有 Critic `<ref>` 文本，不新增模型调用。

原始 A/B 在本代内固定。两个输入相同仍执行既定融合槽位；输入或输出失败按 §3.11 处理。角色字段和输出要求只在 §3.4 详细定义。

### 3.9 本代反思、三方向精英变异与筛选

末轮融合后，Q/E 按 Prompt 9 结合短期反思与目标变化分别总结本代经验，Integrator 只合并这两份文本。随后对本代最初的 A、B 各生成 Q/E/I 三类变异，共六个；Prompt 10 每次只读取一个精英代码、对应本代经验与此前角色历史。

代末候选池严格采用 Algorithm 1 第 34–41 行：EoH 输出、最后轮 Q/E/融合实际输出、末轮精英融合、六个变异。先合法性准入与代码去重，再按统一 Fitness 取 Top N。原父代、启动状态与早轮提案不自动保留；不足 N 时该代失败。

筛选完成后，将本代 Q/E/I 长期反思按角色和代次追加到历史，供后续代使用；该写入时点是本项目执行约定。本代变异同时读取本代经验和此前历史，变异结果不倒灌改写已形成的反思。每次独立研发运行重建历史，实际上下文截断方式在接入时登记。

## 候选合法性检查与失败处理

### 3.11 失败与异常处理

以下是论文未细化部分的本项目执行合同。语法、接口、越权修改、运行异常、非法数值或非法解与目标表现差分别判断；完整有效但较差的结果仍获正常 Fitness。

当前版本不执行候选代码自动修复。技术错误只记录原提案 ID、代码、错误原因、已有 stdout／stderr 与实际开销，不退回原生成方，也不因该错误额外生成修复候选或重评原提案。

- 启动提案无效：沿用 B 作为生成状态。
- 正式轮次提案无效：下一轮沿用该分支上一有效状态，失败提案不冒充本轮有效输出。
- 融合输入缺失：控制程序跳过该槽位；融合或变异输出无效：放弃该输出。
- 初始化或代末有效不同候选不足 N：停止并记录失败，不补入额外提案或旧父代。
- 超时、部分评价、非有限值、非法解：不获正常 Fitness；超时后输出只留作诊断。
- 环境或评价脚本故障：单独记为基础设施问题，不交给模型改评价规则。目标计算或合法性检查存在语义错误时暂停该任务，修正后重新核验受影响结果。

### 3.12 停止与最终程序选择

达到本阶段代数、预算不足以支持下一完整代、用户停止或基础设施不可信时停止。未完成代不记为完成。

研发结束从最后一个完整有效种群按训练 Fitness 选定程序，同分按生成顺序。冻结 Thought、Code 与参数后，按正式测试合同评价；测试结果不反馈搜索或触发重新选程序。P0 只完成工程验收，不产生正式性能结论。

## 本机运行与阶段入口

首版使用 Windows、本机 Python／PowerShell 和独立子进程。所有模型调用通过已有 Codex CLI 的 ChatGPT 登录接入当前订阅的 GPT-5.6 Luna（`gpt-5.6-luna`），不使用思考强度参数。P0 任务1已核验单次提案与反思输出；任务评价、完整控制流程和长历史上下文仍待验证。

并发、线程与资源限制按运行前可用资源和合同确定，进程保持 Normal 优先级。普通子进程不提供容器级隔离；依赖、用户级配置和模型服务变更遵循项目门禁。
